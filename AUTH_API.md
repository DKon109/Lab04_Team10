# Authentication API — Sprint 1

## Base URL

Local backend: `http://localhost:8080`

Send registration and login requests with:
`Content-Type: application/json`

Protected endpoints require:
`Authorization: Bearer <token>`

## Endpoints

| Method | Path | Authentication | Success |
|---|---|---|---|
| POST | /api/auth/register | Not required | 201 Created |
| POST | /api/auth/login | Not required | 200 OK |
| GET | /api/auth/me | Bearer token | 200 OK |

## Authentication rules

- Public registration accepts only `@uni.sydney.edu.au` email addresses.
- Registration passwords must be 8–72 characters long.
- Public registration always creates a `STUDENT` account.
- Login returns an opaque Bearer token with a 3,600-second lifetime.
- Missing, invalid, or expired tokens are rejected on protected endpoints.
- Registration, login, and current-user responses exclude passwords
  and password hashes.

## Contract alignment note

The current backend and frontend use `GET /api/auth/me`.
Some Jira descriptions refer to `GET /api/users/me`.
This discrepancy still needs to be reconciled; this document describes
the currently implemented endpoint.

## Register a student

`POST /api/auth/register`

Authentication is not required.

### Request

```json
{
  "email": "student@uni.sydney.edu.au",
  "password": "StrongPassword123!"
}
```

### Success response — 201 Created

```json
{
  "id": 1,
  "email": "student@uni.sydney.edu.au",
  "role": "STUDENT"
}
```

The ID is generated by the database; `1` is an example.
Registration does not issue a token. Log in after registering.

### Error responses

| Status | Cause |
|---|---|
| 400 Bad Request | Missing or invalid fields, or a non-USYD student email |
| 409 Conflict | The email address is already registered |

Error response examples are provided in the shared error section below.

## Log in

`POST /api/auth/login`

Authentication is not required.

### Request

```json
{
  "email": "student@uni.sydney.edu.au",
  "password": "StrongPassword123!"
}
```

### Success response — 200 OK

```json
{
  "id": 1,
  "email": "student@uni.sydney.edu.au",
  "role": "STUDENT",
  "token": "<issued-token>",
  "tokenType": "Bearer",
  "expiresInSeconds": 3600
}
```

The ID and token above are examples.
Use the actual returned token in subsequent requests:

```http
Authorization: Bearer <issued-token>
```

The token expires 3,600 seconds after issuance.
Log in again to obtain a new token after it expires.

### Error responses

| Status | Cause |
|---|---|
| 400 Bad Request | Missing email or password, or invalid email format |
| 401 Unauthorized | Incorrect email or password |

An unknown email and an incorrect password both return
`Invalid email or password`, so the response does not reveal
whether an email address is registered.

## Get the current user

`GET /api/auth/me`

A valid Bearer token is required. No request body is needed.

### Request

```http
GET /api/auth/me HTTP/1.1
Host: localhost:8080
Authorization: Bearer <issued-token>
```

Replace `<issued-token>` with the token returned by login.

### Success response — 200 OK

```json
{
  "id": 1,
  "email": "student@uni.sydney.edu.au",
  "role": "STUDENT"
}
```

The values above are examples. The response identifies the user
associated with the supplied token and excludes password data.

### Error responses

| Status | Cause |
|---|---|
| 401 Unauthorized | Missing, invalid, or expired token |

## Shared authentication error responses

Validation failures, duplicate registration, invalid credentials,
and authentication or permission failures use these common fields:

| Field | Meaning |
|---|---|
| status | HTTP status code |
| error | HTTP error name |
| message | Explanation of the failure |
| path | Requested API path |
| errors | Field-specific validation messages, when applicable |

### Validation failure — 400 Bad Request

Example: registration without an email address.

```json
{
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/auth/register",
  "errors": {
    "email": "Email is required"
  }
}
```

The `errors` object contains one message per invalid field.
Business-rule errors, such as a non-university email, may omit it.

### Invalid credentials — 401 Unauthorized

```json
{
  "status": 401,
  "error": "Unauthorized",
  "message": "Invalid email or password",
  "path": "/api/auth/login"
}
```

### Missing, invalid, or expired token — 401 Unauthorized

```json
{
  "status": 401,
  "error": "Unauthorized",
  "message": "Authentication is required",
  "path": "/api/auth/me"
}
```

### Insufficient permissions — 403 Forbidden

Example: a student attempts to create an event.

```json
{
  "status": 403,
  "error": "Forbidden",
  "message": "You do not have permission to perform this action",
  "path": "/api/events"
}
```

### Duplicate email — 409 Conflict

```json
{
  "status": 409,
  "error": "Conflict",
  "message": "Email is already registered",
  "path": "/api/auth/register"
}
```

## CORS and frontend integration

The backend has a CORS policy for `/api/**`.

| Setting | Value |
|---|---|
| Default allowed origin | http://localhost:5173 |
| Allowed methods | GET, POST, DELETE, OPTIONS |
| Allowed request headers | Authorization, Content-Type |

To allow a different frontend origin, set the backend environment variable
`TIXORA_CORS_ALLOWED_ORIGIN` and restart the backend.
The value must be one origin, including the scheme and port when needed.

The Vite development server also proxies `/api/*` to
`http://localhost:8080`. Requests through this proxy use the Vite origin
from the browser's perspective.

CORS does not replace authentication. Protected endpoints still require
a valid Bearer token.
